# Validation: skill-versioning

Code checked: committed HEAD `c725774`, read with `git show HEAD:<path>`. Line numbers below are HEAD line numbers.

How the runs were done: HEAD was exported with `git archive HEAD` into a temp sandbox, `npm ci --ignore-scripts` was run there, and the CLI was run with `node --import tsx src/index.ts` on Node 24.21.0. Each experiment ("world") had its own `HOME`, `AUGY_HOME` and `XDG_CACHE_HOME` temp dirs. Upstream repos were local git fixtures behind two stand-ins:

- a fake `gh` on `PATH` answering `gh api` calls, with per-repo "unreachable", "404" and "private" flags and a call log;
- a local HTTP stand-in for `api.github.com`, which served giget tarballs (via `GIGET_GITHUB_URL`) and the git-data endpoints that `fileDiff.ts` calls with `fetch`. A preload redirected `https://api.github.com` to it. It could fail tarball downloads on demand and refused private repos to requests without `Authorization`.

Rollback, update-failure and download-failure paths were run for real against files in these temp dirs. A few read-only calls went to public GitHub (`octocat/Hello-World`) to check how the real API handles tree SHAs and short SHAs. Interactive prompts were driven with `expect`. "read" means checked by reading the code only. "ran" means checked by running the experiment described.

## Spec issues

- **"Update never uninstalls" is vague about broken files.** It's unclear whether a skill whose lockfile entry and links remain but whose files are gone counts as "still installed". The verdict here treats a skill no agent can load as not installed. A stricter wording ("every skill's files remain loadable by its agents") would make this testable.
- **"Rollback by SHA prefix" vs. the default install mode.** The scenario doesn't say whether the skill is symlinked. On symlinked installs the first attempt fails (see "Displaced version archived first"). The scenario should state its fixture, as the tasks preamble already says symlinked installs are the default.
- **"Diff installed against a specific SHA", GitHub fallback.** The spec doesn't say whether `<sha>` may be a short prefix that isn't in history. GitHub's git-data API rejects short SHAs (checked: 404), so the requirement needs to say whether augy must resolve them (for example via `commits/<prefix>`) or reject them clearly.
- **"Interactive rollback picker", dates.** "With each entry's install date" doesn't say whether the date must be visible for every row at once. The code shows it only for the focused row.
- **Diff change-summary scenario too narrow.** The "Mixed changes" scenario has no lines starting with `---` or `+++`, so it can't catch the front-matter miscount. Front matter is the normal `SKILL.md` format, and a scenario with it would catch this.
- **"Failures visible to automation" doesn't cover a download failure masked by giget's cache.** In that case nothing fails visibly, because augy believes the upgrade succeeded. The spec should require that the deployed files actually match the recorded SHA.
- **Pinning scope.** "Pin a skill" is limited to `augy update`. The PRD notes that `augy sync` and `augy home pull` upgrade pinned skills. Nothing in this change says whether that's intended, so a reader of the spec could take "pinned" to mean frozen.

## Behavior not covered by the spec

- **giget's cache masks download failures across install and update** (giget 3.2.0 `giget.mjs:462-467`). The cache is keyed by repo plus `main`, not commit, so any failed download quietly installs whatever tarball was cached last, and augy records the new SHA. Ran: see "Failed upgrade".
- **Downloads ignore the default branch and the user's login.** `buildGigetSource` omits the ref (src/github.ts:264-269), giget defaults to `main` (`giget.mjs:35`), and it has no credentials unless `GIGET_AUTH` is set (`giget.mjs:424`). Updates of skills from private repos, or from repos whose default branch isn't `main`, fail at the download step (see the taps-and-discovery validation).
- **`augy sync` uses a third SHA kind and ignores pins.** read: src/commands/sync.ts:117-143 uses `latestShaForPath` (the latest commit touching the path) and compares it with the recorded SHA. There's no `pinned` check, and :244 only carries the flag forward. Skills synced and then updated will always look drifted.
- **The post-upgrade line prints the new SHA twice** (`✓ tdd 9000300 → 9000300`, src/commands/update.ts:218-223).
- **The multiselect starts with nothing selected**, so "upgrade everything" interactively takes manual selection. `required: true` blocks an empty submit.
- **Clack swallows async errors.** While a spinner is active, `@clack/prompts`' `unhandledRejection` listener turns any thrown error into "Something went wrong" with exit 0. Combined with `program.parse()` not awaiting (src/index.ts:459), errors in diff (and any other command that throws inside a spinner) are invisible to users and CI.
- **The unsourced-skill notice is inconsistent.** update says `augy home push` for no-source skills (src/commands/update.ts:79), while `list` says `augy set-source` (src/commands/list.ts:49).
- **Archives orphaned by uninstall.** Archives kept by uninstall are unreachable after a reinstall, because history starts empty and uninstall only prompts when `history.length > 0`.

## PRD factual errors

Claims in `docs/prd/skill-versioning.md` that HEAD contradicts:

- **Further Notes, "A failed download leaves the skill broken … the skill is left empty for every linked agent, while the lockfile still records the old SHA."** True only when giget has no cached tarball for the repo. Normally the install leaves one behind. In that case (ran) a failed download is masked: giget extracts the stale cached tarball, augy reports success, and the lockfile records the new SHA while the files are the old version.
- **Further Notes, "Diff errors are uncaught. Running diff on a skill with no source … prints a raw error."** For a skill with no source (and for upstream-fetch failures and renamed upstreams), no raw error is printed. Clack's spinner handler prints only "▲ Something went wrong" and the command exits 0 (ran). A raw stack trace appears only for errors thrown before a spinner starts (no active agent, missing installed path, mode-3 missing archive).
- **Further Notes, "Upstream diff likely fails for skills from multi-skill sources (inferred)."** Confirmed by running: it fails, and the failure is silent with exit 0. Public GitHub also returns 404 for `git/commits/<tree-sha>`.
- **Further Notes, open question on short SHAs in the mode-2 fallback.** Settled: GitHub's `git/commits/<7-char-sha>` returns 404 (checked against public GitHub), so a short SHA that isn't in local history can't be fetched.
- **Further Notes, "Rollback is broken for symlinked installs … This needs confirming."** Confirmed on Node 24.21 by running: first attempt fails, empty archive left, second attempt "succeeds", rolling forward restores an empty skill. Node 18 and 20 not tested.
- The other Further Notes were confirmed as stated: spurious drift (a, b), symlinks turned into copies, exit status, name fallback, home-repo substring match, `GITHUB_TOKEN`-only diff fetch, history containing the current version, `archivePath` ignoring `AUGY_HOME`, sync ignoring pins (read).
