# Validation: taps-and-discovery

Code checked: committed HEAD `c725774`, read with `git show HEAD:<path>`. Line numbers below are HEAD line numbers.

How the runs were done: HEAD was exported with `git archive HEAD` into a temp sandbox, `npm ci --ignore-scripts` was run there, and the CLI was run with `node --import tsx src/index.ts` on Node 24.21.0. Each experiment used its own `HOME` and `AUGY_HOME` temp dirs. A fake `gh` on `PATH` answered `gh api` calls from local git fixture repos. It supported per-repo "unreachable", "404/no access", "private" and "truncated tree" flags, and logged every call. A local HTTP stand-in for `api.github.com` served tarballs to giget (via `GIGET_GITHUB_URL`) and refused private repos to requests without an `Authorization` header. Interactive prompts were driven with `expect`. Nothing touched the real `~/.augy` or the real agent folders. "read" means checked by reading the code only. "ran" means checked by running the experiment described.

## Spec issues

- **Tap removal confirmation default.** "Warn and confirm before removing a tap" doesn't say what the default answer is. The code defaults to Yes, so Enter removes the tap. The spec can't catch a destructive default as written.
- **Prompt text vs. repo root.** "Prompt for subdirectory when --path is omitted" covers the default and a custom value, but not how a user picks the repo root at the prompt. With the code as written they can't. Either the spec should require a way to get the root interactively, or it should say explicitly that only `--path ""` gives the root.
- **"List registered taps" with a zero count.** The only scenario uses a count of 2, so it can't catch the count being hidden when it's 0. The requirement text says the count is always shown, so the scenario is weaker than the requirement.
- **Ambiguity within one tap.** "Choose among ambiguous bare-name matches" says the picker covers matches within one tap, but has no scenario for it and doesn't require candidates to be told apart (for example by path). The lockfile is keyed by name, so only one of them can ever be installed anyway. That's worth stating.
- **Tap failures during bare-name resolution.** No requirement says what happens when a tap can't be reached during `augy install <name>`. As written, "not found in any tap" passes the spec even when the real cause is a failing tap.
- **"Discovery uses only GitHub..." vs. installing.** The requirement stops at resolution, so a private tap that resolves but can't be installed passes. The spec should either extend the guarantee to the download step or state that limit openly.

## Behavior not covered by the spec

- **Installs from private taps fail, and the command exits 0.** giget downloads with no credentials (src/github.ts:347-354, giget 3.2.0 honors only `GIGET_AUTH`, `giget.mjs:424`). Ran: `install one --yes` from private `acme/internal-skills` printed `✗ one — Failed to download …: 404`, then "Done!", exit 0, and left an empty `store/one/` directory.
- **Install failures exit 0 generally.** src/commands/install.ts:209-219 catches per-skill errors, then writes the lockfile and prints "Done!". This was seen with the private-repo and `trunk`-branch installs above.
- **A stale giget cache can mask download failures.** giget falls back to its cached tarball when a download fails (giget 3.2.0 `dist/_chunks/giget.mjs:462-467`). The cache key is repo plus ref (`main`), not commit. Ran (skill-versioning experiment): a failed download "succeeded" with old files. This affects installs from taps too.
- **Search status ignores the source repo.** A skill installed from repo X shows as "up to date" or "update available" against a different tap's same-named skill (by design per the PRD, but risky).
- **Default branch vs. download ref** (see "Taps track the default branch"): any source whose default branch isn't `main` can be discovered but not downloaded.
- **Malformed taps are hard to remove.** The `acme/` and `https:/` taps created from bad URLs fail on every search. `tap remove https://github.com/acme` would match `acme/` again through the same parser.
- **Truncation warning on stderr.** The warning is printed with `console.warn` while a spinner is drawing on stdout. In search, the warning isn't tied to any tap heading.

## PRD factual errors

Claims in `docs/prd/taps-and-discovery.md` that HEAD contradicts:

- **Testing Decisions: "An argument without `owner/repo` is rejected."** Only true for shorthand. Ran: `https://github.com/acme` and `https://www.github.com/acme/skills` are accepted and stored as malformed taps (`acme/`, `https:/`).
- **Trust model: "Taps always track the repo's default branch."** True for discovery only. Downloads use giget's default ref `main` (ran with a `trunk`-default fixture: `tarball/main` requested, 404).
- **Further Notes, first bullet: "The same thing happens for skills installed directly by `owner/repo/path/to/skill`."** Only partly true. A direct-path install records the branch commit SHA from the start, so the first `augy update` does not upgrade it spuriously (ran: no upgrade offered while upstream was unchanged). It does show "update available" in search permanently when a tap lists it (ran), and it drifts on every commit to the repo (see skill-versioning validation).
- **Testing Decisions: "`tap list` shows … the count of installed skills from each tap."** The count is printed only when it is above 0 (src/commands/tap.ts:174).
- **Further Notes, "Large repos are silently truncated."** The body is accurate, but "silently" isn't quite right: a stderr warning is printed. The problem is that the warning claims a fallback that never happens.
- The other Further Notes were confirmed: tap errors hidden when nothing matches, resolution hiding tap failures, indistinguishable within-tap ambiguity, the misleading path prompt, typos getting registered, private download failure (now confirmed by running, no longer only inferred), README prerequisites and `GITHUB_TOKEN` text, and name-only status.
